क्लाइंट/VPN कनेक्शन टूटने पर भी बिल्ड और कोडिंग एजेंट चलते रहें; उसी इंटरैक्टिव शेल, वैरिएबल और कार्य डायरेक्टरी से फिर जुड़ें; सहेजा आउटपुट देखें—सीमित रीप्ले, पूरा लॉग नहीं। दोनों तरफ Windows; होस्ट चालू और उपयोगकर्ता लॉग इन रहे। होस्ट रीबूट या लॉग आउट के बाद पुनर्प्राप्ति नहीं।

*यह कार्यप्रवाह का चित्र है, वास्तविक सत्र का स्क्रीनशॉट या परीक्षण का प्रमाण नहीं। चित्र के लेबल अंग्रेज़ी में हैं। मुख्य बात: क्लाइंट का कनेक्शन टूटने के बाद उसी शेल, वैरिएबल और काम पर लौट सकते हैं, यदि होस्ट चालू है और उपयोगकर्ता लॉग इन है। होस्ट रीबूट होने के बाद प्रक्रियाएँ सुरक्षित नहीं रहतीं।*

- **क्लाइंट के बिना भी काम चलता रहे।** बिल्ड, एजेंट और लंबे कमांड दूरस्थ Windows होस्ट पर चलते रहते हैं, चाहे क्लाइंट बंद हो, VPN टूटे या लैपटॉप पुनः शुरू हो।
- **खाली शेल नहीं, उसी काम पर लौटें।** उसी इंटरैक्टिव शेल प्रक्रिया से फिर जुड़ें, उसके वैरिएबल और कार्य डायरेक्टरी सहित।
- **आपकी अनुपस्थिति का आउटपुट देखें।** फिर जुड़ने पर सहेजा टर्मिनल आउटपुट रीप्ले होता है; भंडारण सीमित है, कुछ हिस्से छूट सकते हैं और यह पूरा लॉग नहीं है।

सामान्य गैर-इंटरैक्टिव कामों के लिए आपका मौजूदा, स्वीकृत दूरस्थ कमांड माध्यम पर्याप्त हो सकता है। क्लाइंट बंद होने, VPN टूटने या लैपटॉप फिर शुरू होने के बाद **होस्ट पर चल रहे उसी इंटरैक्टिव Windows शेल और उसके परिवेश** से दोबारा जुड़ना हो, तो दस्तावेज़ में दी गई कनेक्शन शर्तों और स्थानीय नियंत्रण सीमाओं के अनुसार arTerm चुनें। दोनों तरफ Windows चाहिए; होस्ट चालू रहे और उपयोगकर्ता लॉगिन बना रहे। यह होस्ट के रीबूट के बाद प्रक्रियाएँ वापस नहीं लाता।


कनेक्शन टूटे, काम नहीं। बिल्ड, लंबे कमांड और कोडिंग एजेंट दूरस्थ Windows पर चलते रहते हैं। क्लाइंट बंद होने, VPN टूटने या लैपटॉप पुनः शुरू करने के बाद उसी शेल, वैरिएबल और कार्य डायरेक्टरी पर लौटें।

चलता हुआ शेल दूरस्थ होस्ट पर रहता है; लैपटॉप केवल उससे जुड़ता है।

दोनों ओर Windows, टनल के लिए वही GitHub खाता और बाहर जाने वाले कनेक्शन की अनुमति चाहिए। होस्ट चालू रहे और उपयोगकर्ता लॉग इन रहे। होस्ट रीबूट, लॉगआउट, क्रैश, बंद होने या शेल exit के बाद प्रक्रिया वापस नहीं आती। वर्तमान डाउनलोड विकास-हस्ताक्षरित हैं, सार्वजनिक रूप से विश्वसनीय प्रोडक्शन बिल्ड नहीं।

## आवश्यकताएँ और भरोसा

क्लाइंट और होस्ट दोनों पर Windows चाहिए। होस्ट चालू रहे और उपयोगकर्ता लॉग इन रहे। क्लाइंट Microsoft devtunnel CLI और होस्ट संगत नेटिव VS Code tunnel CLI, जैसे code-tunnel.exe, इस्तेमाल करता है। पूरा एडिटर वैकल्पिक है। दोनों टनल में एक ही GitHub खाते से लॉग इन करें; gh का प्रमाणीकरण अलग है। बाहर जाने वाले कनेक्शन की अनुमति, निर्भरता डाउनलोड के लिए सहमति और VS Code server लाइसेंस स्वीकार करना आवश्यक है।

[Windows डाउनलोड](https://github.com/yeelam/arterm/releases/latest) से x64 या ARM64 चुनें। प्रकाशित v0.7.1 विकास प्रमाणपत्र से हस्ताक्षरित है, सार्वजनिक रूप से विश्वसनीय प्रोडक्शन प्रमाणपत्र से नहीं। इंस्टॉलेशन या प्रमाणपत्र पर भरोसा जोड़ने से पहले Get-FileHash से [ZIP की तुलना](../../DEVELOPMENT-INSTALL.md#verify-the-downloaded-release-payload-before-trust-or-installation) उसी रिलीज़ की सार्वजनिक चेकसम सूची से करें। ZIP हैश, CER पहचान और निष्पादन योग्य फ़ाइल की Windows ट्रस्ट स्थिति अलग जाँच हैं। चलाने से पहले निकाले गए इंस्टॉलर और क्लाइंट की [केवल-पढ़ने वाली जाँच](../../DEVELOPMENT-INSTALL.md#inspect-extracted-executable-signatures-without-running-them) Get-AuthenticodeSignature से करें: निर्धारित विकास हस्ताक्षरकर्ता मिलना चाहिए और स्थिति Valid होनी चाहिए। चेकसम अनुपलब्ध या अलग हो, हस्ताक्षरकर्ता अज्ञात हो या स्थिति Valid न हो तो रुकें। प्रमाणपत्र पर भरोसे के लिए अलग से उपयोगकर्ता की स्पष्ट मंज़ूरी और संगठन की नीति की अनुमति चाहिए; उसके बाद फिर जाँचें। OS चेतावनियाँ, Authenticode, SmartScreen या एप्लिकेशन नियंत्रण को दरकिनार न करें।



होस्ट को नीति द्वारा अनुमत Windows Script Host/VBScript भी चाहिए। भरोसा/इंस्टॉलेशन से पहले जाँचें; रोक हो तो रुकें, नीति को दरकिनार न करें।

## सेटअप

सहेजे गए टर्मिनल आउटपुट, सामान्य शेल इतिहास और रिकवरी फ़ाइलों में कमांड, पथ, कोड या गोपनीय जानकारी हो सकती है। दोनों मशीनों पर सुरक्षित रखें और लॉग, स्क्रीनशॉट या सहायता सामग्री साझा करने से पहले संवेदनशील जानकारी छिपाएँ। क्रेडेंशियल का DPAPI संरक्षण यह नहीं बताता कि हर फ़ाइल एन्क्रिप्टेड या सामग्री-रहित है। तैयारी की जाँच के लिए बनाए गए डायग्नोस्टिक रिकॉर्ड में कुछ सामग्री शामिल नहीं की जाती; यह सीमा सभी सत्र डेटा पर लागू नहीं होती।

जाँच सफल होने और नीति की अनुमति के बाद दूरस्थ होस्ट पर arTerm-Host-Setup.exe चलाएँ और नया PowerShell खोलें:

```powershell
arterm-host setup --name my-devbox
```

टनल लॉगिन पूरा करें और होस्ट द्वारा दिखाया गया पंजीकरण कमांड रखें। स्थानीय मशीन पर arTerm-Client-Setup.exe इंस्टॉल करें, नया PowerShell खोलें और उसी GitHub खाते से होस्ट का सटीक पंजीकरण कमांड चलाएँ; वास्तविक होस्ट पथ उसी आउटपुट से लें। क्लाइंट पहले से आरंभ किया गया है; arterm setup आवश्यक नहीं। नए सत्र नाम से स्थानीय मशीन पर कनेक्ट करें:

```powershell
arterm connect my-devbox MyProof --shell powershell
```

## उसी शेल की जाँच

जुड़े हुए दूरस्थ PowerShell में चलाएँ और PID व डायरेक्टरी नोट करें:

```powershell
$artermProof = 'kept-on-host'
$artermPid = $PID
$artermCwd = (Get-Location).Path
$PID; $artermProof; (Get-Location).Path
```

Ctrl+] दबाकर क्लाइंट अलग करें। टर्मिनल शॉर्टकट रोकता हो तो केवल स्थानीय क्लाइंट टैब बंद करें। होस्ट चालू और उपयोगकर्ता लॉग इन रहे। स्थानीय मशीन पर वही कमांड फिर चलाएँ:

```powershell
arterm connect my-devbox MyProof --shell powershell
```

दोबारा जुड़े दूरस्थ PowerShell में:

```powershell
$PID; $artermProof; (Get-Location).Path
($PID -eq $artermPid) -and ($artermProof -eq 'kept-on-host') -and ((Get-Location).Path -eq $artermCwd)
```

अपेक्षित परिणाम: वही PID, kept-on-host, वही डायरेक्टरी और True। बाद में काम जारी रखने के लिए वही कनेक्शन कमांड इस्तेमाल करें। परीक्षण समाप्त करने के लिए दूरस्थ शेल में exit लिखें: प्रक्रिया समाप्त होती है और उसकी चलती स्थिति वापस नहीं मिलेगी।

## सीमाएँ

होस्ट रीबूट, लॉगआउट, क्रैश, बंद होने या शेल से बाहर निकलने के बाद प्रक्रियाएँ पुनर्जीवित नहीं होतीं। होस्ट उपयोगकर्ता लॉगिन पर शुरू होता है; स्वतः लॉगिन या बिना लॉग इन उपयोगकर्ता की सेवा नहीं बनाता। आउटपुट दोबारा दिखाने की संग्रह सीमा है। पूरी विकास शाखा रिलीज़-योग्य नहीं है: फ़ाइल ट्रांसफ़र आर्काइव की स्वतंत्र समीक्षा और सीधे इनपुट की शर्तें अभी अधूरी हैं। मनमाने TUI व्यवहार का प्रमाणन नहीं किया गया है; फ़ाइल स्वतः अनब्लॉक होना सुरक्षा का प्रमाण नहीं।



दोबारा दिखाया गया आउटपुट सीमित है; पूरा आउटपुट चाहिए तो दूरस्थ बिल्ड लॉग रखें। arterm-host stop स्वतः फिर शुरू हो सकता है; arterm-host stop --disable बंद स्थिति बनाए रखता है।

## रिकवरी और बदलाव वापस लेना

विफल होने पर arterm doctor my-devbox से खाते और नेटवर्क जाँचें; ज़रूरत हो तो arterm --login से क्लाइंट लॉगिन सुधारें। रिकवरी रिकॉर्ड न मिटाएँ और चल रहे होस्ट को पुनः इंस्टॉल न करें। अपडेट सामान्यतः सक्रिय सत्रों को बाधित करने से इनकार करते हैं। होस्ट पर arterm-host stop --disable बंद स्थिति बनाए रखता है; arterm-host start फिर शुरू करता है, खोए शेल वापस नहीं लाता। अनइंस्टॉल उपयोगकर्ता डेटा रखता है; प्रमाणपत्र का भरोसा हटाने के लिए गाइड देखें।

## उन्नत स्थानीय नियंत्रण

प्रबंधित send/read के लिए नया समर्थित PowerShell/pwsh सत्र और कनेक्शन से मेल खाती विश्वसनीय स्थानीय पहचान चाहिए। पुराने शेल में एकीकरण नहीं जोड़ा जाता। रिलीज़ शाखा के सीधे इनपुट/ट्रांसफ़र आर्काइव समीक्षा की शर्तें पूरी नहीं करती; अज्ञात संस्करण अप्रमाणित हैं।



Copilot CLI, Claude Code, Codex, Gemini CLI, Kimi और Qwen CLI उपयोगकर्ता सामान्य Windows कमांड चला सकते हैं यदि उनके उपकरण अनुमति दें; यह छह क्लाइंट के नेटिव एकीकरण का प्रमाणन नहीं है। दूसरे स्थानीय नियंत्रण टर्मिनल को वही उपयोगकर्ता, लॉगिन सत्र, इंटीग्रिटी/उन्नत अधिकार संदर्भ और बाइट-दर-बाइट समान विश्वसनीय हस्ताक्षरित क्लाइंट चाहिए। कनेक्शन प्रक्रिया चलती रहे। यह अलग मशीनों के मनमाने एजेंट साझा करना नहीं है।
